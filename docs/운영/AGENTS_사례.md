### 사례 — 묻고 싶은 것을 직접 묻지 않았다 (2026-09-08)

`npm run shot` 이 **Vercel 배포보다 먼저 찍혀서** 옛 화면을 캡처했다. 나는 그걸
보고 "아직 안 고쳐졌다"고 판단했는데, 커밋은 이미 올라가 있었다.

내가 처음 적은 안내는 *"Vercel 배포는 1~2분 걸립니다"* 였다.
**사람이 시계를 보고 기다리게 만드는 안내는 실패한다.** 기다림은 도구가 해야 한다.

그래서 `ship` 이 배포 반영을 기다리게 만들었다 — **판정을 `/_next/static/` 청크
해시 비교로 했다.** 그리고 그게 바로 다음 실행에서 틀렸다:

`scripts/ship.mjs` 하나만 바꾼 커밋은 **클라이언트 번들이 한 글자도 안 바뀐다.**
Vercel 은 정상 배포했는데 청크 해시는 그대로다. 대기가 3분을 꽉 채우고
**"3분 안에 안 바뀜 — 배포 로그를 확인하세요"** 라는 틀린 경고를 냈다.

규칙:

- **묻고 싶은 것을 직접 물어라.** 알고 싶은 것은 "지금 떠 있는 커밋이 무엇인가"
  였는데 나는 "번들이 바뀌었나"를 물었다. 대부분은 두 답이 같아서 프록시가
  통하지만, **갈리는 경우가 바로 문제가 생기는 경우다.**
- 그래서 `app/version/route.ts` 가 `VERCEL_GIT_COMMIT_SHA` 를 그대로 내놓고,
  `ship` 은 그것이 로컬 HEAD 와 같아질 때까지 기다린다. 프록시가 아니라 답이다.
- **답이 안 올 수 있는 경우를 구분해서 말하라.** `/version` 이 아직 배포에 없는
  첫 실행에서는 영원히 기다리게 하지 않고 "건너뜀 — 다음부터 동작합니다"라고 찍는다.

### 사례 — 병목을 분석하면서 그 병목을 다시 밟았다 (2026-09-08)

사용자가 물었다: *"너가 이런 판단들이 계속 병목현상처럼 틀리고 있잖아, 이 간극을
줄이려면 어떻게 해야 할까?"*

나는 답을 **측정으로 받치겠다**며 이렇게 세었다.

```
grep 'e.name'   scripts/*.mjs  →  8건
grep '?? 0'     scripts/*.mjs  →  13건
```

그리고 *"문서에만 있어서 아무도 안 잡는 규칙 위반 21건"* 이라고 보고했다.

**21건 전부 오탐이었다.** 하나도 위반이 아니었다.

- `e.name` 8건 중 **에러는 0건**이다. 전부 `Dirent.name` — `readdir(…, {withFileTypes:true})`
  로 받은 **파일 이름**이다. 실제 에러 처리 두 곳은
  `e.name === "AbortError" ? "시간초과" : e.message` 로, **정확히 규칙대로** 쓰고 있었다.
- `?? 0` 13건은 전부 `(map.get(k) ?? 0) + 1` 카운터 관용구, 헤더 기본값, 그래프 인접
  리스트 `?? []` 다. 판정 경로에는 하나도 없다. `fetch-course-routes.mjs` 는 이미
  **없는 snap 값을 실패로 처리한다.**

무엇을 틀렸나 — **위 3문의 ①이다.** 알고 싶었던 것은
*"오류 메시지를 버리는 코드가 있나"* 인데, 나는 *"`e.name` 이라는 글자가 있나"* 를 물었다.
문자열 검색은 그 질문의 프록시고, 이 경우 프록시와 답이 완전히 갈렸다.

규칙:

- **grep 히트 수를 발견으로 보고하지 마라.** 히트는 후보다. 위반이라고 말하려면
  **한 건씩 열어 봐야** 한다. 세는 것은 읽는 것을 대신하지 못한다.
- **자기 진단을 뒷받침하는 숫자일수록 더 의심하라.** 이 숫자는 내 논지("문서 규칙은
  안 지켜진다")에 딱 맞았고, 그래서 검증하지 않았다. **원하는 답이 나올 때가 가장 위험하다.**
- 처방도 바뀌었다. "문서 규칙을 검사로 내린다"는 층은 **대상이 0건**이라 할 일이 없었다.
  실제로 필요했던 것은 **이 3문**이다 — 검사를 하나 더 만드는 게 아니라, 보고하기 전에
  ①을 통과시키는 것.

### 사례 — 3주를 끈 사이트 전체 버그는 `<svg><title>` 한 줄이었다 (2026-09-08)

배포된 **모든 페이지**에 React 하이드레이션 오류(#418)가 있었다. React 가
**서버 HTML 을 통째로 버리고 다시 그린다.** 그 과정에서 내가 head 에 꽂은
Leaflet 스크립트가 날아간 적도 있다(그때 나는 "지도가 고장났다"고 오진했다).

**그런데 화면은 정상으로 보인다.** 그래서 아무도 몰랐다.

원인:

```tsx
<svg role="img" aria-labelledby={`cf-${name}-t ...`}>
  <title id={`cf-${name}-t`}>{name} 구간 도식</title>   // <- 이 한 줄
```

React 19 는 `<title>` 을 **문서 메타데이터로 보고 `<head>` 로 올린다.**
SVG 안이라도 클라이언트 경로에서 그 구분을 못 한다. 서버는 SVG 안에 그리고
클라이언트는 올려버려서 트리가 어긋난다. 접근성 이름은 `aria-label` 로 주면 된다.

왜 이제야 찾았나 — **찾을 수단이 없었다.** 운영 배포는 오류 번호만 주고,
전문은 개발 모드에서만 나온다. 나는 개발 서버와 브라우저를 동시에 붙일 수 없다.
`npm run shot:local` 을 만든 뒤 **한 번에** 나왔다. 도구를 만든 것이 진단이었다.

규칙:

- **`<svg>` 안에 `<title>` 을 쓰지 마라.** `aria-label` + `<desc>` 를 쓴다.
  `npm run check:cdn` 이 이제 이것도 막는다.
- **화면이 정상으로 보이는 버그가 가장 오래 산다.** 콘솔을 자동으로 모아라.
- 그 검사를 만든 직후 **오탐 5건**이 났다 — 내가 방금 쓴 **주석 안의 `<title>`**
  을 코드로 읽었다. 규칙을 설명하는 문장이 그 규칙 위반으로 잡히는 꼴이다.
  **범위를 넓히면 오탐부터 잡아라** — 오탐이 남은 검사는 사람이 곧 무시한다.

### 사례 — 원인을 하나로 단정했다 (2026-09-08, 위 사례의 후속)

뚝섬 경로선이 한강을 가로지른 원인을 나는 **"내가 hint 좌표를 지어냈기 때문"**
이라고 단정했다. 지어낸 것은 사실이고 그건 그것대로 잘못이다. 그래서
hint 를 공식 자양역 좌표로 바꾸고 **고쳤다고 적었다.**

다시 돌리니 **완전히 같은 값이 나왔다** — 2.24km, 점 5개, 비율 1.01배.
경로는 그대로 강을 가로지른다. 즉 **hint 는 원인의 일부였을 뿐이고,**
진짜 원인은 그 bbox 안 길들의 연결 구조(강을 건너는 비-교량 연결)다.

두 가지 규칙:

1. **"고쳤다"는 다시 돌려서 값이 바뀐 것을 보고 말하라.** 원인을 하나 찾아
   고치면 그게 유일한 원인이었다고 믿기 쉽다. 같은 입력에 같은 출력이면
   아무것도 안 고친 것이다.
2. **잘못이 두 개면 하나를 고쳐도 증상은 남는다.** 지어낸 좌표(잘못 A)를
   고치는 것과 경로가 강을 건너는 것(증상 B)은 별개였다.

임시 처방: 「희박하면서 곧은 선」 검사를 넣었다(점/km < 3 이고 비율 < 1.05).
잠실 4.9점·1.12배, 반포 9.4점·1.15배는 통과하고 뚝섬 2.2점·1.01배만 떨어진다.
**이건 어림짐작이라고 코드에 적어 뒀다** — 수치로 "선이 물 위에 있다"는 확인할
수 없다. 뚝섬은 경로선 없이 두고, 화면으로 확인될 때까지 그대로 둔다.

### 사례 — 숫자는 전부 통과했는데 선이 한강을 가로질렀다 (2026-09-08)

`npm run shot` 을 만들어 **처음으로 배포 화면을 직접 봤다.** 뚝섬 지도에서
경로선이 **강 위를 직선으로 가로지르고 있었다.**

그런데 내 검사는 전부 통과였다:

| 지표 | 값 | 판정 |
|---|---|---|
| 길이 / 양끝 직선 | 1.01배 | 통과 (1.0 이상) |
| 점 개수 | 5개 | 통과 (4개 이상) |
| 끝점 보정 | 334 / 219m | 통과 (700m 이하) |

**전부 정상 범위다.** 수치로는 잡을 수 없었다.

원인은 더 나빴다. 뚝섬에는 공식 자료에서 확인한 공원 진입 지점이 없었다.
그래서 나는 스크립트에 이렇게 적었다:

> *"두 끝점의 중간을 **북쪽으로 400m 옮긴 점**을 쓴다 — 뚝섬은 북쪽 강변이다."*

**좌표를 지어낸 것이다.** §1 이 금지하는 바로 그것이고, 주석에 근거처럼 적어 둬서
더 그럴듯해 보였다. 그 점이 강 위/엉뚱한 길에 붙어 경로가 그쪽으로 갔다.

세 가지 규칙:

1. **입력을 지어내면 검사가 무의미하다.** 검사는 출력이 말이 되는지 보는데,
   입력이 가짜면 "말이 되는 가짜"가 통과한다. 지어낸 값에는 검사를 붙일 수 없다.
2. **파생할 수 있는 값을 손으로 적지 마라.** 지금 이 스크립트는 좌표를
   `lib/courses.ts`(출처·확인일이 붙은 원장)에서 읽는다. 진입 지점이 없는 코스는
   **건너뛴다** — 지도는 그 코스만 경로선 없이 그려진다.
3. **화면으로만 잡히는 결함이 있다.** 수치 검사를 아무리 늘려도 "선이 물 위에
   있다"는 못 잡는다. 그래서 `npm run shot` 이 검사기 목록만큼 중요하다.
   내가 화면을 못 보는 동안 이 결함은 **배포된 채로 살아 있었다.**

같은 실행에서 화면으로만 잡힌 것 둘 더:
   · 거리 칩이 줌 버튼과 겹쳐 **"편도" 두 글자가 가려졌다.**
   · U턴 핀이 강 가운데(다리 위)에 떠서 **경로선과 이어지지 않았다.**
둘 다 코드로는 정상이고, 픽셀로는 틀렸다.

### 사례 — `?? 0` 하나가 검사를 껐다 (2026-09-08)

경로선 검사에 "끝점 보정이 700m 를 넘으면 실패"를 넣었다. 그리고 검사가
읽을 값을 원장에 남기게 했다. 그런데 **필드를 나중에 추가했다.**
그 전에 저장된 여의도 항목에는 값이 없었고, 내 코드는 이랬다:

```js
snapFromM: r.snapFromM ?? 0,
```

**0m 는 완벽한 값이다.** 그래서 보정 939m 짜리 — 선이 U턴 핀에 닿지도 않는 —
경로가 검사를 통과해서 배포됐다. 사람이 화면에서 볼 때까지 아무도 몰랐을 것이다.

세 가지가 겹쳤다:

1. **없는 값에 관대한 기본값을 줬다.** 이건 검사를 끄는 것과 같다.
   모르면 **모른다고 실패**해야 한다.
2. **원장에 없는 값은 검사할 수 없다.** 검사 항목을 늘릴 때는 그 값이 원장에
   기록되는지 같이 확인해야 한다.
3. **네트워크 실패와 판정 실패를 같게 다루지 않은 건 옳았다** — 서버가 죽었다고
   좋은 데이터를 지우면 안 된다. 그런데 그 결과로 **나쁜 옛 값이 살아남았다.**
   두 정책이 다 맞는데 조합이 틀린 경우다. 그래서 `--check` 를 별도 관문으로 둔다.

규칙: **검사에 필요한 값이 없으면 통과가 아니다.** `?? 0`, `|| ""`,
`?.length ?? 0` 같은 기본값을 검사 경로에 쓰지 마라 — 판정을 무조건 통과로
바꾸는 방향이면 특히.

### 사례 — 검사가 옳은 데이터를 버렸다 (2026-09-08)

경로선 검사에 이 규칙을 넣었다. 규칙 자체는 맞다:

> **길은 두 끝점 사이 직선거리보다 짧을 수 없다.**

그런데 **비교 대상이 틀렸다.** 나는 *다리 좌표* 사이 직선과 비교했는데,
경로가 실제로 잇는 것은 **강변에 스냅된 점**이다. 다리는 강 가운데에 있으니
스냅에서 400~600m 가 빠진다. 그래서:

| | 값 |
|---|---|
| 여의도 경로 | 1.01km |
| 다리 좌표 사이 직선 | 1.15km → **"불가능한 값"으로 판정** |
| 실제 양 끝점 사이 직선 | (스냅 기준) 1.01km 보다 작다 → **정상** |

**서로 다른 두 점 사이의 거리를 비교했으니 애초에 판정할 수 없는 값이었다.**
검사가 멀쩡한 데이터를 버렸다. 잠실도 2.49 → 2.88km 로 바뀌어 비율이
1.3배에서 1.12배가 됐다 — 원래 값이 더 그럴듯하다.

규칙:

- **검사를 만들 때도 같은 것끼리 비교하는지 먼저 확인하라.** 부등식이 참이어야
  하는 관계인지(경로 ≥ 같은 두 점 사이 직선) 따져야, 위반이 곧 오류가 된다.
- **검사가 틀리면 옳은 데이터를 버린다.** 통과 못 한 항목을 버리는 설계
  (여기서는 "쓰지 않는다")는 검사가 정확할 때만 안전하다.
- 질문을 섞지 마라. "경로 길이가 말이 되나"와 "끝점이 엉뚱한 데 붙었나"는
  다른 질문이고, 지금은 다른 지표로 본다(`ratio` / `snapFromM`).

### 사례 — 오류를 `e.name` 만 찍어서 원인을 지웠다 (2026-09-07)

406 을 고치면서 User-Agent 를 붙였다. 이렇게 썼다:

```js
const UA = "ddaiga-americano/1.0 (러닝 코스 경로선; https://...)";
```

**HTTP 헤더 값은 ASCII(ByteString)만 허용된다.** Node 는 이걸 정확히 알려준다:

```
TypeError: Cannot convert argument to a ByteString because the character
at index 22 has a value of 47084 which is greater than 255
```

그런데 내 catch 는 `e.name` 만 담았다. 사용자 화면에 남은 것은 이랬다:

```
overpass-api.de TypeError / kumi.systems TypeError / private.coffee TypeError
```

**세 서버가 전부 죽은 것처럼 보인다.** 실제로는 요청이 나가지도 않았다.
index 22 라고 정확히 짚어 주는 메시지를 내가 버렸다.

규칙:

- **오류는 `name` 이 아니라 `message` 를 찍는다.** `cause?.code`(ENOTFOUND,
  ECONNREFUSED 등)도 같이 찍는다. 이름만 남기면 진단이 사라진다.
- **헤더 값·URL·파일명에 한글을 넣지 마라.** 이 저장소는 주석과 사용자 문구를
  한글로 쓰지만, **프로토콜 값은 ASCII 다.**
- 같은 실수를 두 번 했다는 점이 중요하다. 406 사례는 "상태코드를 원인으로 번역
  하지 마라"였고, 이번은 "원인을 아예 지워 버렸다"다. 둘 다 **진단 정보를 다루는
  방식**의 문제다. 실패 경로의 출력은 성공 경로만큼 신경 써서 만들어라 —
  실패 메시지는 사람이 다음에 무엇을 할지 정하는 유일한 입력이다.

### 사례 — 406 을 "서버 혼잡"으로 읽었다 (2026-09-07)

`npm run routes` 가 사용자 PC 에서 전부 실패했다.

```
overpass-api.de 406 / kumi.systems 429 / private.coffee 429
```

내 스크립트는 이걸 **"Overpass 공개 서버 혼잡일 가능성이 큽니다 — 나중에 다시
실행하세요"** 로 안내했다. **틀렸다.** 406(Not Acceptable)은 혼잡이 아니라
**"이 요청은 받아들일 수 없다"**는 뜻이다. 원인은 서버가 아니라 내 코드였다.

빠져 있던 것 둘:
1. Overpass 문서 형식은 `data=<urlencoded>` + `application/x-www-form-urlencoded`.
   나는 질의문을 그대로 body 에 넣었다. **브라우저에서는 됐다** — 브라우저 fetch 가
   붙여 주는 `text/plain` 을 서버가 관용적으로 받아 줬기 때문이다. Node 는 안 된다.
2. **User-Agent 가 없었다.** Overpass 예절과 미러들의 차단 규칙이 요구한다.
   미러의 즉각적인 429 도 혼잡이 아니라 이것 때문일 가능성이 크다.

두 가지 규칙:

- **상태코드를 원인으로 바로 번역하지 마라.** 이 저장소에 이미 있던 교훈의 반대편이다
  (거기서는 200 을 성공으로 읽었고, 여기서는 4xx 를 남의 탓으로 읽었다).
- **잘못된 안내는 침묵보다 나쁘다.** "나중에 다시 실행하세요"는 사람을 영원히
  기다리게 한다. 지금은 상태코드별로 *서버 혼잡* 과 *질의 형식 거부(코드 문제)* 를
  나눠서 찍는다. **사람이 할 일이 다르면 문구도 달라야 한다.**
- 브라우저에서 되는 요청이 Node 에서 된다고 가정하지 마라. 헤더 기본값이 다르다.

### 사례 — 없으면 지어내지 말고 **찾아라** (2026-09-07)

코스 지도에 **경로선을 그리지 않았다.** 이유는 이렇게 적어 뒀다:

> 산책로 실제 경로 좌표를 나는 갖고 있지 않다. 다리 좌표를 이어 선을 그으면
> 강 위를 가로지르는 엉뚱한 선이 된다.

걱정은 옳았다. **결론이 틀렸다.** 사용자가 그걸 한 문장으로 짚었다 —
*"맵 보고 모르면 그냥 나가는 거야."* **경로선 없는 코스 지도는 코스 지도가 아니다.**

한강 자전거길은 **OSM 에 이미 그려져 있다.** 지도 타일에 보이는 그 선이다.
Overpass 로 받아 최단경로를 구하면 실제 선형과 실제 거리가 나온다.
"내가 가진 데이터에 없다"를 "존재하지 않는다"로 읽은 것이 잘못이다.

**작화 금지 규칙의 목적은 페이지를 비워 두는 것이 아니다.** 비우기는 확인이
불가능할 때의 최후 수단이고, 그 전에 **확인할 방법을 찾는 것**이 먼저다.
규칙을 방패로 쓰면 사용자가 쓸 수 없는 페이지가 남는다.

같이 나온 검사 규칙 하나 — **길은 직선거리보다 짧을 수 없다.**
첫 시도에서 여의도 0.91km(직선 1.1km), 잠실 2.24km(직선 2.5km)가 나왔다.
불가능한 값이다. 원인은 경로가 다리 위 자전거길로 강을 건너 질러갔고(전자),
다리를 전부 빼자 지천 교량에서 길이 끊긴 것(후자)이었다.
비율 검사 한 줄이 둘 다 잡는다. `npm run check:routes` 가 이걸 본다.
**통과 못 한 코스는 파일에 쓰지 않는다 — 틀린 선은 선이 없는 것보다 나쁘다.**

### 사례 — "지도가 안 뜬다"의 원인은 내 관측 환경이었다 (2026-09-07)

**먼저 정정.** 바로 아래 사례에서 나는 "배포된 화면에서 지도 4개 중 3개가
안 떴다"고 단정했다. **그 단정은 근거가 부족했다.**

내가 브라우저를 자동화로 몰던 탭은 `document.visibilityState === "hidden"`
이었다. 숨은 탭에서는 브라우저가 프레임을 그리지 않고, 그러면

* `requestAnimationFrame` 이 **아예 안 온다**,
* `IntersectionObserver` 콜백도 **전달되지 않는다**.

지도는 `IntersectionObserver` 로 화면에 들어올 때만 만든다. 즉 **숨은 탭에서는
설계상 절대 안 뜬다.** 사용자 화면의 고장이 아니라 관측 장치의 성질이다.
확인 방법도 이걸로 갈렸다 — 스크린샷을 찍어 강제로 렌더시키자
그 순간 지도가 생겼다.

증거가 어긋난 것도 있었다. 나는 "요청은 200인데 `window.L` 이 undefined"를
근거로 들었는데, 그 리소스 기록이 **내가 직전 호출에서 직접 실행한 `fetch()`**
와 구분되지 않는다. 같은 파일을 두 경로로 받아놓고 한쪽만 세었다.

규칙:

1. **자동화 브라우저로 본 화면을 사용자 화면이라고 부르지 마라.**
   화면을 판정하기 전에 `document.visibilityState` 와 rAF 도착을 먼저 확인한다.
   숨어 있으면 그 관측은 버린다.
2. 화면 판정은 **사람에게 확인을 받아라.** 나는 렌더링되는 창을 못 가진다.
3. **내가 만든 네트워크 요청과 페이지가 만든 요청을 섞어 세지 마라.**

아래 사례에 적은 세 가지 수정(CDN 제거·DOM 소유권 분리·타임아웃)은 그대로 둔다.
셋 다 원인 진단과 무관하게 옳은 변경이다. 다만 **"운영에서 깨져 있던 것을
고쳤다"고 말할 근거는 없다.**

### (근거 부족) 사례 — 200으로 성공한 스크립트가 실행되지 않았다 (2026-09-07)

> ⚠️ 위 정정을 먼저 읽어라. 아래 관측 상당수가 숨은 탭에서 나온 것이다.


코스 페이지 지도 4개 중 3개가 안 떴다(한 번은 4개 다). 남는 화면은
**"지도 불러오는 중…" 한 줄**이다. 실측:

| 본 것 | 값 |
|---|---|
| leaflet.min.js 네트워크 요청 | **200**, 37KB, 417ms |
| `window.L` | `undefined` |
| head 에 꽂은 `<script>` 태그 | **DOM 에 없음** |

요청은 성공했고 스크립트는 실행되지 않았다. 그러면 `onload` 도 `onerror` 도
오지 않아 Promise 가 **영원히 pending** 이다. 그래서 오류 문구조차 안 뜬다.

배경: 모든 페이지에 React 하이드레이션 불일치(#418)가 있어서 React 가 서버
HTML 을 버리고 다시 그린다. 그때 **내가 손으로 꽂은 노드가 같이 날아갔다.**

세 가지 규칙이 나왔다.

1. **외부 CDN 스크립트를 손으로 꽂지 마라.** npm 의존성 + `await import()` 를 쓴다.
   번들러가 코드 분할까지 해주고, React 와 문서를 다투지 않는다.
   `npm run check:cdn` 이 이걸 막는다.
2. **한 DOM 노드를 React 와 라이브러리가 같이 소유하게 하지 마라.**
   Leaflet 컨테이너 div 에 React 가 자식(로딩 안내문)을 렌더하고 있었다.
   안내문은 형제 오버레이로 빼야 한다.
3. **모든 로딩 상태에 타임아웃을 넣어라. 영원한 로딩 표시는 오류보다 나쁘다** —
   기다리면 될 것처럼 보이니 사람이 떠나지도 알리지도 않는다.

그리고 **"차단도 결품도 200으로 온다"에 하나 더 붙는다 — 실행 실패도 200으로 온다.**

### 사례 — "고아 페이지"라는 진단이 틀렸다 (2026-09-06)

Search Console 이 **색인 11 / 미색인 33**, 사유 100% "발견됨 — 현재 색인이
생성되지 않음"을 보여줬다. `/courses` 검사에는 **"참조 페이지: 감지된 페이지 없음"**.
서브에이전트(seo-auditor)도 "compare 22개 중 18개가 고아"라고 짚었다.
두 근거가 맞아떨어져서 나는 **"고아 페이지가 원인으로 확인됐다"**고 적었다.

그 다음 날 `check:internal` 을 만들어 실제로 링크 그래프를 세어 보니,
**고아는 0개였다.** 52개 라우트 전부에 인바운드가 있었고, sitemap 도 전부 일치했다.
compare 18개는 그 전에 이미 고쳤는데 내가 그 사실을 진단에서 빼먹었다.

무엇을 잘못했나 — **GSC 문구를 코드 사실로 번역했다.**
"참조 페이지: 감지된 페이지 없음"은 *"링크가 없다"*가 아니라
*"링크가 걸린 페이지를 구글이 아직 크롤하지 않았다"* 일 수도 있다.
색인이 11개뿐이니 후자가 오히려 자연스러웠다. 나는 두 해석 중
**내가 이미 갖고 있던 가설과 맞는 쪽만 골랐다.**

서브에이전트 결론이 겹친 것은 독립 근거가 아니었다 —
같은 저장소를 같은 시점에 본 것이라 같은 착시를 공유한다.
**두 근거가 같은 곳에서 왔으면 하나로 세라.**

규칙: 외부 도구의 문구를 원인으로 옮겨 적기 전에, **그 주장을 저장소에서
직접 셀 수 있는지 먼저 보라.** 셀 수 있으면 세고, 세었으면 검사기로 남겨라.
